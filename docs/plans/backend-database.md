# LEVNAT Backend and Database Plan

The first release should let an operator find and read inquiries from `/contact/` and Galaxy in both themes. Start with the existing Node.js intake and add PostgreSQL when the operator needs a durable inbox or the deployment needs shared storage. The current file store already supports durable intake on one host. [Contact form](../../website/src/studio/app.js#L58) · [Galaxy form](../../website/src/galaxy/js/ui.js#L151) · [File store](../../website/src/server/inquiry-store.mjs#L212)

## Architecture

The protected site serves the forms and `/api/inquiries` from the same HTTPS origin. NGINX enforces the existing strict PQC transport policy and proxies intake to Node.js over a private Unix socket. Node.js accesses a private PostgreSQL instance. The GitHub Pages workflow publishes a standalone static bundle. Confirm the production hostname and deployment topology before provisioning. [Protected deployment](../../deploy/pqc/README.md#hosted-instance) · [Pages workflow](../../.github/workflows/pages.yml)

Start with one `inquiries` table. Use `id UUID PRIMARY KEY` for the existing receipt, `sealed_payload BYTEA` and `signature BYTEA` for the original bytes, and key identifiers for selecting encryption and verification keys. Keep the envelope version in the signed payload. Store `received_at TIMESTAMPTZ` as indexed metadata for chronological listing and retention, derived from the verified payload on import. Keep contact details, project description, service, budget, and timeline inside the encrypted payload. Keep keys outside PostgreSQL and recoverable separately from database backups. [Encryption and signing](../../website/src/server/inquiry-store.mjs#L66)

## Implementation phases

1. **Confirm the operator workflow.** Identify the operator, production hostname, existing file records, retention period, and acceptable data loss and recovery time. Use those requirements to choose where PostgreSQL runs and how it is backed up. The first operator workflow is a private chronological list with receipt and timestamp plus the existing `read <receipt>` command. Add workflow statuses, notifications, or an authenticated web inbox when daily use calls for them. [Operator CLI](../../website/src/server/inquiries.mjs#L186)
2. **Add PostgreSQL storage.** Create versioned SQL migrations and implement the existing `put` and `read` behavior against a real PostgreSQL test instance. Preserve validation, rate limits, AES-256-GCM encryption, and ML-DSA-87 signature verification. Under Read Committed, insert with `ON CONFLICT (id) DO NOTHING` and, on conflict, fetch the committed row in a subsequent statement, verify and decrypt it, and compare normalized fields. Return the same `201 {id}` after a durable commit or a matching retry. Return `409` for a different body on the same receipt and `503` when storage is unavailable. [API handler](../../website/src/server/inquiries.mjs#L146) · [PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html) · [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)
3. **Connect readiness and operations.** Replace the unconditional NGINX `204` on `/api/inquiries/ready` with a bounded probe of the app and storage. Preserve `204` with `X-Inquiry-Transport: strict-pqc-v1` for the healthy path. Return `503` for storage failure and map unavailable or timed-out readiness upstreams to `503` at NGINX. Keep the database private and separate runtime, migration, and operator access. Monitor write errors, latency, and backup status without logging inquiry bodies. Rehearse a database restore and private read with the stored keys before directing public traffic to PostgreSQL. [Client contract](../../website/src/shared/secure-inquiry.js#L70) · [NGINX readiness configuration](../../deploy/pqc/nginx.conf.template#L87) · [PostgreSQL backup formats](https://www.postgresql.org/docs/current/app-pgdump.html)
4. **Stage and switch.** Test the production topology with synthetic data. If real file records exist, rehearse a repeatable import that verifies each signature and copies the original sealed payload and signature bytes. Pause intake, let active requests finish, take a file snapshot, run the final import, and reconcile receipt IDs and sealed bytes before switching and reopening intake. During rollback keep PostgreSQL as the source of records accepted since the switch. If returning to files, pause writes and reconcile those records into the file store before reopening intake. [Protected deployment acceptance](../../deploy/pqc/README.md#acceptance-before-switching-the-public-domain)

Daybook is a separate product decision. A live booking system would need its own model for availability, bookings, and concurrent slot allocation. The demo currently uses sample data and keeps bookings in page memory. [Daybook source ownership](../../README.md#source-ownership)

## Release checks

The current file-backed baseline passed all five `npm run test:pqc` tests. The PostgreSQL, hosted, and migration checks below are deferred to implementation.

- [ ] Run the existing API tests against the file store and the PostgreSQL adapter. Verify concurrent identical and conflicting submissions, a retry after a lost acknowledgment, and persistence after restart.
- [ ] Stop Node.js and PostgreSQL in staging. Verify readiness returns `503`. Stop storage during submission and verify the form retains input and never shows success for an uncommitted write.
- [ ] Import a synthetic legacy store twice, reject a tampered record, and reconcile IDs, bytes, and signatures. Restore the database into an isolated environment with the corresponding keys and confirm the operator can list and read a known receipt. Rehearse rollback after accepting a new record in PostgreSQL.
- [ ] Confirm synthetic personal data stays encrypted in database rows and backups and is absent from diagnostic logs. Verify that public requests cannot read receipts and that deployment artifacts exclude private code, credentials, and records.
- [ ] Submit from `/contact/` and both Galaxy themes on the staging origin using desktop and phone browsers. Check receipt display and operator discovery for each submission. Run `deploy/pqc/check.mjs` against staging and verify any deployed alias, address family, and TLS termination point.
