# Website design research and practice

Reusable reference for mobile and desktop websites. Sources checked November 13, 2026. For page structure, navigation trees and user journeys, see [Website mapping research](website-mapping-research.md).

Use this reference when reviewing a design, choosing between variants, or writing acceptance checks. WCAG criteria are cited by level. Published studies describe the people, devices and tasks they tested. Values marked **LEVNAT default** are starting points to validate for each project.

## Design decisions that apply across devices

| Decision         | Working rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Page purpose     | Make the heading describe what the visitor can do or learn. Give the primary action a specific label and a clear position. Keep an alternate route available for visitors who have a different goal.                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Visual hierarchy | Use position, size, weight, contrast and whitespace to separate the main action from supporting content. Group a heading with its description, a service with its action, and an error with its field.                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Reading order    | Structure headings, lists and landmarks in HTML. Keep meaningful reading and tab order as components move between columns. Put distinctive words early in headings and links. [WAI page structure](https://www.w3.org/WAI/tutorials/page-structure/) · [WCAG meaningful sequence](https://www.w3.org/TR/WCAG22/#meaningful-sequence)                                                                                                                                                                                                                                                                                             |
| Typography       | Define a small scale for body text, labels and headings. Use relative sizes and allow wrapping and text enlargement. **LEVNAT default** — start body text around 1rem with a unitless 1.5 line height and aim for roughly 65–75 characters on longer English prose lines. Verify with the actual font, language and content. Use display typography for short headings where it stays legible. [USWDS typography](https://designsystem.digital.gov/components/typography/) · [GOV.UK layout](https://design-system.service.gov.uk/styles/layout/) · [GOV.UK type scale](https://design-system.service.gov.uk/styles/type-scale/) |
| Spacing          | Use shared spacing values for repeated components. Keep related elements closer together than unrelated sections. Increase margins on wide screens where they help orientation. Inspect short pages and real content extremes before adopting a scale. [GOV.UK spacing system](https://design-system.service.gov.uk/styles/spacing/)                                                                                                                                                                                                                                                                                             |
| Components       | Use links for destinations and buttons for actions. Give each interactive component a visible label or recognizable icon with an accessible name. Specify rest, hover where available, focus, selected, disabled, loading, error and success states where they apply.                                                                                                                                                                                                                                                                                                                                                            |
| Themes           | Use semantic tokens for surfaces, text, actions, borders and status. Use the system preference for the initial palette where appropriate and respect an explicit visitor choice. Verify contrast and native controls in each palette. Keep navigation, labels and task context consistent across the theme change. [MDN prefers-color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-color-scheme) · [MDN color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme)                                                                          |
| Evidence         | Match evidence to the question. A screenshot can show visual emphasis. A live task shows whether someone understood the label, acted successfully and recovered. Use project analytics for the device mix and observed tasks for visitor behavior.                                                                                                                                                                                                                                                                                                                                                                               |

## Research findings and limits

**Link clarity and contrast affect search effort.** A 2025 controlled study showed 102 participants pairs of web-page variants, covering 11 pages. Lower contrast and less clear links made tasks harder on the study pages. The effects of icon changes varied with context. Participants were primarily computer science students. The result supports making a primary action visibly actionable and pairing unfamiliar icons with labels. It gives no effect size for a specific client site. [Sensors, October 3, 2025](https://doi.org/10.3390/s25196101)

**A visual anchor can attract attention before visitors read the supporting copy.** A 2026 digital-museum study combined ratings from 70 participants with eye tracking from 40. Large images, especially those with simple motion, often drew early fixations. The eye-tracking group consisted of young adults recruited from one university, and the study focused on initial attention and appeal. For Galaxy, use the scene to convey what the site does, and test whether a visitor can also identify the offer and find a next action. [Fang et al., Scientific Reports, May 18, 2026](https://doi.org/10.1038/s41598-026-51528-5)

**A stretched desktop layout can separate information people need together.** In a qualitative desktop study, Nielsen Norman Group compared compact and dispersed homepage and product page prototypes. Five people participated in pilots and eight saw the final prototypes. The researchers observed that larger imagery, text and gaps sometimes pushed related details apart and required extra scrolling. Use a bounded content column and keep controls and supporting information close to their subject. The study supplies a design hypothesis, and its small laptop sample gives no universal page width. [NN/g findings and methodology, October 13, 2023](https://www.nngroup.com/articles/content-dispersion/) · [Study design](https://www.nngroup.com/articles/content-dispersion-methodology/)

**Visitors use several ways to scan text.** NN/g’s eye-tracking work describes heading-led and word-led scanning, as well as an F-shaped gaze pattern on some prose-heavy pages. Tasks, formatting and writing direction matter. Use descriptive headings, visible labels and predictable alignment so visitors can find information even when reading selectively. [NN/g text-scanning research, 2019](https://www.nngroup.com/articles/text-scanning-patterns-eyetracking/)

**Mobile navigation should explain where a visitor landed.** Baymard observed retail participants who opened navigation after arriving directly on a product page. An unmarked current category made orientation harder. Separately, GOV.UK’s topic-page A/B comparison found slightly higher link click-through and less time on the list variant than the grid variant. Retail product pages and government topic pages have different tasks from LEVNAT. Apply the findings by testing whether a service title, a clear current section and a visible return help people starting from search. [Baymard mobile research, updated July 14, 2026](https://baymard.com/research-articles/mobile-ux-ecommerce) · [GOV.UK topic-page experiment, January 31, 2025](https://insidegovuk.blog.gov.uk/2025/01/31/rolling-out-simpler-ways-to-navigate-gov-uks-topic-pages/)

**Form layout affects recovery and order.** Baymard’s checkout research observed visitors skipping or misreading fields in multicolumn forms and struggling when a label disappeared during typing. These are retail observations. Start a service inquiry with one column, persistent labels and only the fields needed to respond, then test with the mobile keyboard open. [Baymard form research, updated June 9, 2026](https://baymard.com/blog/form-design) · [WAI form labels](https://www.w3.org/WAI/tutorials/forms/labels/)

**A theme needs its own visual review.** Research on alternative color modes in mobile apps documented benefits tied to users’ needs and accessibility problems in existing implementations. Apply this as a reason to test both site palettes, including images, text, focus and control states. The study concerns mobile apps and supplies no universal ranking of light and dark website themes. [Andrew and Tigwell, ACM, September 2025](https://doi.org/10.1145/3743704)

## Mobile and desktop composition

| Aspect                | Narrow viewport and touch                                                                                                                                                                                                              | Wide viewport and mixed input                                                                                                                                                                                                      |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First screen          | Show the page purpose, an action and the start of useful content. Check the height with browser controls visible. Give interactive media enough space for accurate touch while keeping the HTML route discoverable.                    | Use the extra width for a scene plus its controls or relevant supporting details. Keep the offer and action close enough to the visual that visitors can take in both.                                                             |
| Layout                | Start with one reading column. Let buttons and labels wrap. Open a breakpoint when the real content needs room. Check landscape and the on-screen keyboard.                                                                            | Use columns when content has a clear relationship, such as details with a supporting image. Bound text width independently of a full-bleed image or scene. Check ordinary laptop windows and the transition to compact navigation. |
| Navigation            | Keep the menu button reachable and show the current section or page. Put a direct route to the most important task outside collapsed navigation when the screen permits. Give overlays a close action and a logical focus destination. | Use inline navigation when the labels fit. Show the current section. Make dropdowns operable by click and keyboard, and check that pointer movement between the trigger and panel keeps the panel usable.                          |
| Secondary information | Show a short summary first and expand more detail on request. Provide a visible route to all options when a strip can scroll sideways.                                                                                                 | Display related details together when comparison is useful. Use headings and short lists so users can scan across sections. Preserve the same actions in resized and zoomed windows.                                               |
| Feedback              | Show confirmation close to the tapped control. Keep errors and progress visible as the viewport changes. Provide a visible alternative for swipe and drag actions.                                                                     | Show a clear focus and hover state. Keep popovers within the usable viewport and support keyboard and mouse. Provide feedback during transitions and return focus when the UI closes.                                              |

Start with intrinsically flexible CSS. Use Grid or Flexbox for structure, viewport queries for page-wide changes and container queries when a reusable component needs to adapt to its own space. Base breakpoints on labels, line lengths and controls fitting. Use pointer and hover features to enhance behavior, because a wide display can have touch and a small display can have a keyboard or mouse. Keep critical content available without hover. [web.dev breakpoints](https://web.dev/learn/design/media-queries) · [MDN container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries) · [MDN media queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Media_queries/Using)

For a standard navigation menu, use a named `nav`, links and a disclosure button that exposes its expanded state. For a true modal, move focus into it, contain Tab while open, give it a close action, and restore focus to the opener or a logical next element. Apply the modal pattern only when the rest of the page is actually inactive. A passive hologram should leave focus on the control the visitor is using. [WAI disclosure navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/) · [WAI modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

### Forms and status feedback

- Give each control a visible associated label. Provide field purpose and any required format before entry. Use appropriate types and autocomplete tokens, such as `type="email"` and `autocomplete="email"`. Keep the submit action reachable with the mobile keyboard open. [WAI forms tutorial](https://www.w3.org/WAI/tutorials/forms/) · [WHATWG autocomplete](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#autofill)
- On failure, keep the entered values and explain how to correct the problem beside the field. For several errors, a focused summary with links to the fields can speed recovery. Distinguish invalid fields, a failed request, a request in progress and a confirmed success. [GOV.UK validation pattern](https://design-system.service.gov.uk/patterns/validation/) · [WCAG status messages](https://www.w3.org/TR/WCAG22/#status-messages)

## Accessibility and motion

Use WCAG 2.2 AA as the design baseline. The December 2024 publication is a W3C Recommendation. The September 2026 WCAG 3 publication is a Working Draft. These checks cover common design risks. Use a representative evaluation and complete task journeys for a conformance assessment. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) · [WCAG 3.0](https://www.w3.org/TR/wcag-3.0/) · [WCAG-EM 2.0, July 2026 Group Note](https://www.w3.org/TR/WCAG-EM/)

| Check                        | Requirement or project default                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reflow and text              | At a width equivalent to 320 CSS px for vertically scrolling content, preserve information and function without two-axis scrolling, except where a portion requires a two-dimensional layout for use or meaning. That width corresponds to 400% browser zoom on a 1280 CSS px starting viewport. The corresponding reference for horizontally scrolling content is 256 CSS px in height. Also check 200% text resizing, user-adjusted spacing and both orientations, subject to each criterion. [Reflow](https://www.w3.org/TR/WCAG22/#reflow) · [Resize text](https://www.w3.org/TR/WCAG22/#resize-text) · [Text spacing](https://www.w3.org/TR/WCAG22/#text-spacing) · [Orientation](https://www.w3.org/TR/WCAG22/#orientation)                                                                                    |
| Contrast and state           | WCAG AA uses 4.5:1 for ordinary text and 3:1 for large text. Essential control states and graphical objects require 3:1 against adjacent colors where the non-text contrast criterion applies. Inspect the actual background in both themes, including gradients and moving artwork. Use a text, shape or pattern cue alongside color for important states. [Text contrast](https://www.w3.org/TR/WCAG22/#contrast-minimum) · [Non-text contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast) · [Use of color](https://www.w3.org/TR/WCAG22/#use-of-color)                                                                                                                                                                                                                                                      |
| Touch targets                | The AA minimum is 24 × 24 CSS px, subject to exceptions including spacing, equivalent controls, inline text, browser-controlled size and essential presentation. The enhanced 44 × 44 criterion is AAA with its own exceptions. **LEVNAT default** — aim for a 44 × 44 CSS px hit area on primary standalone controls and check it with overlays present. [AA minimum](https://www.w3.org/TR/WCAG22/#target-size-minimum) · [AAA enhanced](https://www.w3.org/TR/WCAG22/#target-size-enhanced)                                                                                                                                                                                                                                                                                                                       |
| Keyboard, gestures and hover | Check semantic order, visible focus and keyboard activation. At AA, author-created overlays must leave the focused component at least partly visible. Provide a single-pointer route for applicable path gestures and drag functions, subject to the criteria’s exceptions. Extra content triggered by hover or focus must meet the applicable dismissal, hoverability and persistence requirements. [Keyboard](https://www.w3.org/TR/WCAG22/#keyboard) · [Visible focus](https://www.w3.org/TR/WCAG22/#focus-visible) · [Focus not obscured](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum) · [Gestures](https://www.w3.org/TR/WCAG22/#pointer-gestures) · [Drag](https://www.w3.org/TR/WCAG22/#dragging-movements) · [Hover and focus content](https://www.w3.org/TR/WCAG22/#content-on-hover-or-focus) |
| Motion                       | Provide pause, stop or hide for nonessential movement that starts automatically, lasts over five seconds and runs alongside other content. Review flashes under WCAG 2.3.1. Honor `prefers-reduced-motion` in CSS and JavaScript so reduced-motion visitors can complete the same actions. The interaction-animation criterion 2.3.3 is AAA. [Pause, Stop, Hide](https://www.w3.org/TR/WCAG22/#pause-stop-hide) · [Flashes](https://www.w3.org/TR/WCAG22/#three-flashes-or-below-threshold) · [Animation from interactions](https://www.w3.org/TR/WCAG22/#animation-from-interactions) · [W3C reduced-motion technique](https://www.w3.org/WAI/WCAG22/Techniques/css/C39)                                                                                                                                            |

## Media, 3D and performance

1. **Deliver the task before optional visuals finish.** Serve the heading, native links and key actions in HTML. Reserve the scene and image dimensions before loading. Use `srcset` and `sizes` for resolution selection, and `picture` when the composition or format needs to change. Keep a likely LCP image discoverable in the initial HTML and load it eagerly. Use high fetch priority selectively after verifying the LCP element. Lazy-load suitable below-the-fold images. [Responsive images](https://web.dev/learn/design/responsive-images) · [Optimize LCP](https://web.dev/articles/optimize-lcp)
2. **Treat 3D as progressive enhancement.** Expose an equivalent HTML route for every essential scene action. Distinguish loading, first usable frame, unsupported WebGL and lost context. Test whether links and the text quiz work throughout. Pause offscreen or hidden rendering where practical, cap the drawing buffer based on measured device cost, and test context restoration. [WHATWG canvas](https://html.spec.whatwg.org/multipage/canvas.html#the-canvas-element) · [WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) · [Khronos context-loss simulation](https://registry.khronos.org/webgl/extensions/WEBGL_lose_context/)
3. **Track field and lab separately.** Google’s good Core Web Vitals thresholds are LCP ≤ 2.5 s, INP ≤ 200 ms and CLS ≤ 0.1, evaluated at the 75th percentile and segmented by mobile and desktop. Use page-level field data where available and label origin-level data or insufficient coverage. Use repeatable lab profiles to diagnose regressions. Record time to first usable 3D frame and scene responsiveness separately, because these are experience-specific measurements. [Web Vitals](https://web.dev/articles/vitals) · [Lab and field differences](https://web.dev/articles/lab-and-field-data-differences)
4. **Check a real device for graphics work.** In a 2025 Chrome engineering example, one graphics-heavy interaction took 270 ms on a CPU-throttled desktop and 620 ms on a real mid-tier phone. Those are single-demo timings. Use emulation for layout regressions and real phones for graphics, touch and sustained use. The 2025 HTTP Archive sample found good Core Web Vitals on 48% of mobile sites and 56% of desktop sites. Use the site’s own data to prioritize devices. [Chrome DevTools, April 4, 2025](https://developer.chrome.com/blog/devtools-grounded-real-world) · [HTTP Archive 2025 performance chapter, updated May 2026](https://almanac.httparchive.org/en/2025/performance#core-web-vitals-summary)

## Applying the reference to LEVNAT

| View            | What to design and verify                                                                                                                                                                                                                                                   |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Galaxy homepage | Offer a direct path to Services and an optional 3D Quiz. Keep the scene and its controls grouped on desktop. On phones, verify the scene, theme switch and Services entry together at 320 and 390 CSS px. The seven labeled links must reach the same pages as the spheres. |
| Service detail  | Show the service name, outcome, example and relevant next action. Check direct entry from a shared link. Make Back to Galaxy visible and confirm the intended theme, orbit mode and sphere on return.                                                                       |
| Quiz and result | Show progress, the current question and an explicit exit. Let visitors select each answer through visible labeled controls as well as the 3D models. Test navigation backward, theme changes and the move from recommendation to inquiry with visible, editable context.    |
| Contact         | Keep a short, labeled inquiry form. Verify touch, keyboard, text enlargement, recovery from a validation or connection error, and a successful confirmation in an environment configured for intake.                                                                        |

These are review and acceptance targets drawn from external research. LEVNAT visitor outcomes remain to be measured.

## Release checklist

- [ ] Inspect affected views at 320 × 568 and 390 × 844, immediately below and above each changed breakpoint, at a normal laptop size, and in a wide desktop window. Include landscape, 200% text and zoom. These are test fixtures for the project.
- [ ] Test closed and open navigation, both themes, visible focus, Tab and Shift+Tab, reduced motion and relevant touch or pointer interactions. Use at least one real iPhone Safari and one representative Android Chrome device when available. Record unavailable hardware explicitly.
- [ ] Run representative tasks from Home and a direct service link. Record first action, task success, wrong turns, return context and time. Check at least one journey with a screen reader. Use automation for regression checks and manual testing for reading order and usability. [W3C accessibility evaluation](https://www.w3.org/WAI/test-evaluate/) · [GOV.UK moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)
- [ ] For media or 3D changes, capture a cold-load trace, verify the actual LCP element, test slow startup and context loss, and check that core tasks work while the canvas is unavailable. Compare field metrics after release when coverage permits.
- [ ] Record the page, viewport, input, theme, browser, device, build, evidence and result for each important issue. Preserve a screenshot for layout issues and a task recording or trace for interaction and performance issues.

When revisiting this reference, recheck standards, browser support, benchmark dates and the project’s audience data. Keep a change that depends on a study’s finding tied to the task and audience it will be tested with.
